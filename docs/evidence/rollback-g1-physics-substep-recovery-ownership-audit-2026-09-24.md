# G1 PhysX substep recovery ownership audit

Read-only audit of the existing `SoulcaliburVI.exe` Ghidra program (image base `140000000`, game SHA-256 `f8904e4b04bca3b47bc52a683f6190365d2eb89ee8f44f8072759e9c5e04a553`) and current policy-v4 source. No database edit, deployment, or game run was made for this audit.

## Native obligation order

The world start-physics tick (`142018570`, tick vtable `1439EFA78`) reads the world at tick `+0x50`, scene at world `+0x1C8`, and enters `142027E40` for a nonnull scene. That routine calls `1420297F0(scene,0,scene+0x130)`. The latter sets scene active `+0xFE[type]`, replaces the completion-event reference, and dispatches collection `scene+0x10` before making the substep task. In substep mode, `142028440` allocates a `0x40` completion task retaining the event, then queues the initial three-unit graph delegate for named thread 2. After `1420297F0` returns, `142027E40` adds the scene `+0x130` event to a further dependent graph and stores its result at scene `+0x160`.

The initial delegate method `1420555E0` initializes context `+0xB0/+0xB8/+0xBC/+0xC0` and enters `142055C40`. That routine replaces context `+0xC8` event, allocates a `0x40` task retaining it, and schedules the repeat continuation before dispatching `scene+0x80` callbacks. Repeat method `142055BC0` releases context `+0xC8`, then uses unsigned `context+0xC4 < context+0xA0` to schedule another substep or releases the final `+0xB0` owner. `1420113E0` dispatches real callbacks and compacts expired entries; returning or suppressing a callback would change native behavior.

Type-2 scene work also enters `1420297F0` from `142027C10` with scene `+0x140`; that caller creates another dependent graph task and stores scene `+0x158`. The `142017920` caller of `142027E40` runs a six-iteration sequence including scene start, `14202DE80`, and `FinishPhysicsSceneFrame` each iteration. These are native event dependencies, not optional observer notifications.

The installed vehicle callback pair is registered by `1430F5C20`: it calls generic `1421377C0` with `scene+0x10`, owner and method `1430FC2B0`, then `scene+0x80`, owner and method `1430FE7A0`, storing returned handles at owner `+0x60/+0x68`. The generic helper has at least 19 direct callers in this program. It compacts the target collection, increments its count, appends a three-unit delegate and returns a sequence handle. The count/handle snapshot admitted by policy v4 does not itself prove a stable writer generation across another thread. A same-count replacement or unregister/register cycle requires independent writer coverage or a synchronization contract. No such contract was established in this audit.

## Existing mod ownership

`Sc6ReplayTaskGroup::PumpOne` pops a named-thread-2 task and `DispatchTask` validates the exact initial/repeat substep callable before the native wrapper. Policy-v4 failure site 11 records the first failure and terminates. It neither completes nor abandons the native task; it is terminal containment. The existing `ConsumerHeld`/`RequestConsumerResume` path owns an indexed component task through `ConsumerHoldState` and `NativeReplayPrerequisiteGuard`; its validation is specific to task table `1439CD9C0`, function/world/completion fields, an owner index/generation and application epoch. It provides no demonstrated protection or recovery disposition for either substep graph task or its scene/event chain.

**Bounded conclusion:** Holding one popped substep graph task would leave the already published scene active/event state and dependent graph work pending. The available evidence does not establish an abandonment, cancellation, or complete-B recovery protocol for that path. A supported recovery design would need either (a) independently verified ownership of the scene/event/dependent-task chain through a resumable disposition, or (b) a generation-stable callback witness before `1420297F0` publication plus a proved way to recover the enclosing tick task without manufacturing completion. Both remain unproven. This audit does not change the policy-v4 terminal containment result or the separate A210/B217 prerequisite recovery proof.
