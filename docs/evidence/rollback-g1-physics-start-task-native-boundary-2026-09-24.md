The matching end tick vtable is `1439EFA90`, virtual `+8` target `142018350`. Scheduler capture accepts both tables. A PhysX guard must target `1439EFA78`, not the 2D table.

For a non-null scene, `142027E40` calls `142019030` and then `1420297F0(scene,0,scene+0x130)`. `1420297F0` marks `scene+0xFE[type]` active and replaces the completion event reference before it dispatches callback collections `scene+0x10` and, outside substep mode, `scene+0x80`. It later submits or completes scene work. Its callbacks cannot be skipped after event publication without a separate unwind protocol. Substep `142055C40` schedules dependent event/task work before dispatching collection `scene+0x80`; a start-task check alone does not cover later mutation during substeps.

The current `Sc6ReplayTaskGroup::DispatchTask` owns the dequeued native task before `Virtual(task,8,...)`, and the PhysX start wrapper has not entered. Its existing `TerminalFailure` path records failure then halts the owning pump without signaling, recycling or counting the task complete. A second read-only check here could detect a changed callback owner before this wrapper consumes it, but that result is terminal containment, not suspension or complete-B recovery. Any valid-path check must preserve the null-scene native no-op and must forward admitted callbacks exactly once. The existing `GroundDebrisState::physics_step_consumers` predicate at application entry is the applicable prior consumer check; its production reuse at dispatch requires a separate RED/GREEN receipt.

Mutation of `+0x18` alone is therefore not a proved callback-dispatch defect for this delegate; the current owner/method/handle and registration checks remain appropriate.
