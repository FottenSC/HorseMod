## Follow-up: native transform dispatcher and stored-transform readers

A later read-only pass in the same `SoulcaliburVI.exe` program followed the user's narrower question: what does the dispatcher read, write, or call after receiving a debris body pose? No database or production-code edit was made in this pass.

`ApplyPhysicsBodyTransformOutputs` (`142028750`) reads the body pose, compares it with the child's cached `ComponentToWorld` at tolerance `0.0001`, calls child virtual `+0x438 = MovePrimitiveComponent` (`141DA43E0`) with `bSweep=0` on a difference, then calls owner virtual `+0x410` even when the move was skipped. The unswept move calls `USceneComponent_InternalSetWorldLocationAndRotation` (`141DA2820`), which can write relative transform/cache fields and recompute `ComponentToWorld` via `141DB0600`. That recomputation invokes `PropagateSceneComponentTransformUpdate` (`141DA79D0`); the dispatcher therefore **does publish a value for later readers**, not merely a render command.

The two remaining **stored-transform reachability** questions are not answered by inspecting only `142028750`:

* `DispatchReflectedGetGroundDebrisCall` (`140CF1310`) returns the root object through a registered UFunction. Neither the thunk nor the direct native getter reads child pose. A Blueprint or other reflected caller can subsequently traverse the root and read a child; no static direct call xref or negative exact-name package scan establishes that no active caller does so.
* `RefreshNiagaraStaticMeshSource` (`141BC7F90`) is a concrete generic reader of a selected `UStaticMeshComponent`'s `+0x270` transform. Its source selection can use an explicit Source actor or enumerate the Niagara system component's owner through `GetComponentsByClass` (`141C1A0F0`); it copies the transform into the data interface's current/previous matrices and may rebuild mesh section data via `141BCAEB0`/`141BCAAA0`. No examined native path proves an active interface selects a WorldSettings-owned debris child in A617, or that a selected Niagara output feeds combat. The active source actor/system owner and selected weak component must be observed or excluded for the admitted case.

This pass closes the **known immediate dispatch branches conditionally** and identifies the remaining stored-state readers. It does not establish presentation-only debris motion, an actual A617 flag value, or a live gameplay effect. A bounded A617 observation should record child identities plus the guarded callback/volume/navigation predicates and active reflected/Niagara selections; the current independent changed-free-body task regression is still RED, so it does not authorize deployment for that observation.

## Conclusion and next resolving observations

No inspected path demonstrates debris pose or velocity changing fighter damage, movement, hit decisions, or ring-out. A native path **does** propagate that motion into UE component state, and an unguarded physics-volume branch can have callbacks and shared effects. Motion therefore cannot yet be classified as presentation-only for the admitted A617 case. Preserve logical debris lifetime, slot/group operations, callback timing, RNG draws and any discovered shared feedback as authoritative.

The next bounded checks are: (1) witness `component+0x48 & 0x40`, component volume `+0x244`, volume collection, and callback/delegate topology for the selected A617 children; (2) either admit only the inert flag/volume state at the actual native consumption point or capture its effects exactly; (3) close active reflected/Blueprint and Niagara static-mesh readers for that same owner; (4) then run the plan's isolated motion perturbation and independent continuation comparison after the current RED source is repaired and G0 recertified. No broad PhysX task-family investigation is justified by this consumer audit alone.
