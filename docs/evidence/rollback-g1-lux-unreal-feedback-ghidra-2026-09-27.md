With no creation profile, the builder leaves the default white even if a palette pointer exists on the trace data asset. The selected live helper supplied approximately `(4.0,3.8,0.12545,1.0)`, so a default-white source is excluded for that observed call, but the profile-versus-palette source remains unbound. ## Material row and reachable operations

The wrapper at `141F45940` copies exactly 16 bytes into a local `float[4]` and forwards to `SetMaterialInstanceVectorParameter` `141F1E420`. That setter finds or appends a 0x28-byte row at MID `+0xB8`, compares four floats, writes changed values, and calls `DispatchMaterialInstanceVectorProxyUpdate` `141F05150`; it can separately call `RefreshMaterialRenderProxyResources` `141F2ED00`. The proxy dispatch copies the FName, four floats and up to three raw MID proxy addresses into a queued command on the threaded route, or invokes the proxy updater directly. Submission is not completion or an ownership lease.

Independent layout evidence is the native reflection registration `14262C490`: `VectorParameterValue` size `0x28`, `ParameterName` offset `0`, `ParameterValue` offset `8`, `ExpressionGUID` offset `0x18`. The containing UMaterialInstance registration `14261A640` places `VectorParameterValues` at `+0xB8`. The Ghidra `FVectorParameterValue_Partial` type now has `FLuxFName_Partial`, `FVector4`, and `FGuid_Partial` in those exact locations. `DispatchMaterialInstanceVectorProxyUpdate` uses the typed row. `UpdateMaterialInstanceRenderProxyParameters` `141F1A4D0` walks the same array at stride `0x28` and republishes each row, parent and other overrides to proxies. `ClearMaterialInstanceOverridesAndRebuildProxies` `141F14AC0` zeros vector/scalar counts, optionally clears texture/font arrays, resets three proxies directly or by queued task, then invokes the republisher. These are separate operations from one vector write and remain B-undo/completion dependencies.

`UMaterialInstanceDynamic` registers reflected `K2_GetVectorParameterValue` at `14261B960`/`1426251F0`, with a 0x18-byte parameter block holding `ParameterName` at +0 and four-float `ReturnValue` at +8. The native name/target pair at `143ABD5E0` binds that name to reflected thunk `ProcessMaterialInstanceDynamicGetVectorParameterValue` `14262CE00`. The thunk decodes FName from FFrame, calls `GetMaterialInstanceVectorParameterValueOrDefault` `141F3E120`, and returns the color. That wrapper initializes `(0,0,0,1)` then invokes `GetMaterialInstanceVectorParameterValue` `141F1A260`. The latter scans MID vector rows at `+0xB8` with `0x28` stride, copies the exact 16 bytes from a matching row to the output, and returns success; on a miss it can query its parent through virtual `+0x338` under a recursion guard. The assembly uses `MOVUPS` for the 16-byte copy; the decompiler's scalar cast at this point is misleading. The new `UMaterialInstance_VectorLookupPartial` structure records the verified parent `+0x78`, lookup flags `+0x80`, and vector array `+0xB8`. The `KismetMaterialParameterCollectionLibrary` registration at `142493AC0`/`1424A14E0` is a distinct collection getter.

Two generic Lux-side consumers also invoke virtual `+0x338`: `SetCharaMaterialVectorValue` `1403CCCF0` and `SetWeaponMaterialVectorValue` `1403CE930`. Native tables bind their exact reflected names to thunks `140910800` and `1409110B0`, whose direct calls reach these bodies. Each enumerates fighter or weapon materials, accepts a **caller-supplied** FName, queries the current vector value, then sets a new four-float value only if the getter returns success. Their disassembly tests only `AL`; it does not use the returned old color bytes. This establishes a possible parameter-presence gate, not a numerical color-to-gameplay dependency. No retained observation or static binding identifies either routine as a reader of the selected trace MID or its `BaseColor`. Authored asset readers, the selected material/parent graph, and shader uses remain open.

## Shared lifecycle and body path

Start calls `BindLuxTraceVfxFinishedAndResetFadingTraces` `1408CDBB0`, which binds a weak named receiver on VFX manager `+0x388` and mutates fading traces. The reflected thunk `140C40570` calls `ULuxTraceComponent_OnActiveTraceVFxFinished` `1408D3F20` synchronously. That callback clears trace-state `+0xD8`, invokes attachment virtual `+0x238`, and removes exact weak membership at component `+0x3F0`. The exact attachment constructor `1408CC0F0` installs vtable `143360370`; its `+0x238` entry at `1433605A8` points to `UActorComponent_Deactivate` `141D41870`. Deactivation can alter tick/active state and broadcast `OnComponentDeactivated`. Its selected runtime delegate receivers remain unobserved. This finish route is required shared lifecycle regardless of whether color is visual.

On provider replacement, `UMeshComponent_SetMaterial` `141D86410` calls provider virtual `+0x630` and, only after a nonnull result and `HasNativePhysicsBody`, invokes `UpdateBodyInstancePhysicalMaterialState` `142007950`. For the selected trace provider table `1438829C0`, virtual `+0x630` at `143882FF0` points to `GetSkeletalMeshBodyInstanceByBoneName` `142100F30`. Its zero-name route reads the default index `+0xBF0`; the named route resolves a mesh map index. Both require index `< +0xC38` and return a pointer from `+0xC30`. The downstream update resolves physical material, collects component material slots, enters native physics scene work and copies material properties into linked body data. This is a conditional physics feedback path for **material replacement**. The C18 sample did not establish selected body occupancy, so it cannot classify this branch for the selected provider. A vector value write by itself does not call SetMaterial on the inspected path.

The selected provider table's material-count virtual `+0x628` at `143882FE8` resolves to `USkinnedMeshComponent_GetNumMaterials` `141DC8A90`; material slot virtual `+0x4E8` at `143882EA8` resolves to `UMeshComponent_GetMaterial` `141DC8220`. The second returns a nonnull override from component array `+0x808/+0x810` if present, otherwise a skeletal asset row pointer from `+0xA0 + slot*0x30` when within asset count. The helper can therefore traverse current slot results that differ from the entry census. Ghidra now has `USkinnedMeshComponent_MaterialLookupPartial` (0x918 bytes) and `USkeletalMesh_MaterialSlotsPartial` (0xB0 bytes) partials for these verified headers. The containing asset field remains an eight-byte `void *`: an MCP field-type change to the standalone partial pointer unexpectedly produced a four-byte unnamed field, which was restored and verified. This is an unresolved typed-pointer application, not an inferred four-byte pointer.

## Effect-to-combat dependency conclusion

The blanket claim that Unreal effects cannot influence future combat is unsafe. Native `InitializeTilePoolParticleEmitterInstance` `141F9BD00` calls imported UCRT `rand` at `141F9BD56` to seed the emitter-local random stream. `InitializeLuxGroundDebrisComponentRing` calls the same import at `140895D68` and `1408960FF`; combat `LuxMoveVM_ExecuteAndDumpOpcode` calls it at `140366FEE` in opcode `0x50006`, then uses the value to choose a script branch. A read-only parse of all 30 shipped `dump/Battle/cpu/cpuai*.dtp` files through the existing native-bound `parse_move_play_command_table` found 528 definitions containing opcode `0x50006` before their first script end, across all 30 files. This establishes authored availability, not execution of a particular branch in the retained match. The [retained native CRT receipt](rollback-ground-ucrt-live-shared-audio-2026-09-22.json) observed 162 emitter draws and 48 ground-placement draws on one thread during the candidate combat run, with valid native RNG transitions. It did not observe that MoveVM opcode in the sampled ticks or a changed combat outcome. This is a verified shared-state route and a conditional combat dependency, not a live divergence witness. Ghidra's stale EOL comment at `141F9BD56` was corrected and read back.

This finding does not mean rendered pixels or debris child motion feed combat. The [bounded motion perturbation](rollback-ground-motion-probe-2026-09-22.json) changed all five admitted child poses and matched combat, native CRT and logical ground observations for 120 independent continuation ticks after 407 rolling corrections in its recorded configuration. It does not close arbitrary reflected readers, changing listener routes, or every physics consumer. The reflected `GetGroundDebris` thunk `140CF1310` was typed with manager, `FFrame_Partial`, the declared root-component result and signed `nInstanceId`; its direct getter returns a root object rather than a moving child. No general motion-exclusion policy or G1 gate is admitted from these results.
