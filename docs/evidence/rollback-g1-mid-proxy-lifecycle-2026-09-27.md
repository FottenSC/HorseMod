# G1 MID proxy lifetime investigation — 2026-09-27

Read-only investigation in the existing `SoulcaliburVI.exe` Ghidra program (`x86:LE:64:default`, Windows, image base `140000000`). Another `EBOOT.elf` program was current, so every program-scoped MCP request explicitly named `SoulcaliburVI.exe`. No second binary was imported and no Ghidra type, function or database edit was made. The existing `UMaterialInstanceDynamic_Partial` is a 200-byte partial type through its vector header at `+0xB8`; it does not model the proxy and destruction fields below.

The [live C18 diagnostic](rollback-g1-c18-shape-capacity-live-2026-09-27.md) sampled 145 distinct MID addresses and 145 occupied first-proxy slots at `MID+0xF0`, plus two nonempty vector headers at `MID+0xB8`. This is entry data, not a retention lease. The following native path identifies why copying those pointers or treating a submitted task as completed would be unsafe:

| Native site | Observed action | Consequence |
| --- | --- | --- |
| `141F1B3A0`, exact MID vtable `14391EE70` slot `+0x48` | Allocates `0x168` bytes, initializes a proxy through `141F05F10`, stores it at MID `+0xF0`. | The sampled occupied slot denotes a separate native proxy allocation; 145 slots do not prove its complete owned footprint or uniqueness over time. |
| `141F1E420` | Writes/appends a 0x28-byte vector row in the `+0xB8` array, dispatches `141F05150`, and conditionally refreshes `+0xF0` through `141F2ED00`. | MID values, vector backing, proxy rows, and resource state can diverge if only one layer is restored. |
| `141F05150` / callback `141F15FC0` | The queued path copies raw proxy addresses to its command, then the callback mutates proxy `+0x138` parameter rows. | Callback return establishes CPU body completion, not proxy ownership or downstream GPU completion. |
| `141F2ED00` / callback `141F32D90` | A distinct queued refresh copies the first raw proxy pointer and later calls `141F2EC80`, including proxy vslot `+0x28`. | Vector-task completion does not imply refresh-task completion. |
| `141F143C0`, exact MID vtable slot `+0x88` | Calls the base BeginDestroy path, starts proxy resource release via `1415E98A0(MID+0xF0)`, then begins an `FRenderCommandFence` at MID `+0x1B0`. | Submission and BeginDestroy are not a cancellation or a permission to revive a PendingKill MID. |
| `141F1A9E0`, exact MID vtable slot `+0x90` | Returns ready only after base readiness and the MID `+0x1B0` fence probe `1415EE2B0`. | This is a destruction readiness gate. It does not establish all corrected-execution application/render completion for B. |
| `141F162D0`, exact MID vtable slot `+0x98` | Schedules or performs proxy deletion via `141F16380`, clears `+0xF0`, releases twelve cache pointers at `+0x150..+0x1A8`, then calls `UObject_FinishDestroy`. | FinishDestroy has logical and resource effects; a held pointer cannot be used to resurrect the MID. |
| `141F26F50` -> `14161A110`, exact vtable first destructor | Frees the vector backing at `+0xB8` and other array backings; further base destruction follows. | A snapshot of a vector header alone cannot own its backing after native destruction. |

`141F05F10` sets the proxy vtable `143914F78` after a base constructor. `141F16380` may defer proxy deletion through a render-thread task. `1415E98A0` also has immediate, queued and delayed release routes. I did not establish that the MID destruction fence drains both parameter and refresh commands, their downstream resource releases, or the mod's particle GPU query. The [earlier native contract](rollback-g1-finish-material-native-contract-2026-09-27.md) records the vector/refresh builder, callback ABI and separate old-parent fence in more detail.

`FRenderCommandFence_BeginFence` at `1415E9510` receives `false` from MID BeginDestroy. Its deeper RHI/GPU branch is conditional on the argument being true; with false, the threaded path queues the ordinary render-thread fence through `140D205A0` / `140D34880`. The readiness probe at `1415EE2B0` checks that fence task's completion bit. That is not a demonstrated RHI/GPU drain, and native task ordering with the two material command families remains unproved.

The scheduling paths differ before any callback executes. The vector and refresh builders store requested-thread byte `0xFF` in their out cells; their submitters `1421AF910` and `14134C6C0` pass that byte to TaskGraph vslot zero. The ordinary fence builder stores `2`, and `140D34880` submits with `2`. In the actual TaskGraph implementation, constructor `140D180F0` installs vtable `1434B1F20` into the global returned by `140D24400`; its slot zero is `140D2E6C0`. That method sends `0xFF` through its any-thread/worker selection using task-header priority bits when native multithreading is supported, whereas a concrete thread index uses the named-thread queue. No inspected builder supplied an explicit prerequisite linking either material task to the later fence. This is evidence **against assuming** a common serial queue; it does not establish the live configuration's exact worker schedule or prove that a particular material callback outlived the fence. A controlled pending-task/fence experiment is still required before treating any fence as a settlement receipt.

The downstream resource path is separate again. `141F3D330`, called by both proxy vector-row update `141F05460` and resource refresh `141F2EC80`, clears four proxy-held resource-reference slots and can queue last-reference retirement into global deferred queue `144344848`. Consumer `1415DC470` waits RHI command-list graph events through `1415E5360/1415E5490/1415E56D0` and then drains that queue, sometimes across frame counters. Stock global flush path `1415ED320` can reach this consumer and waits its own render fence, but invoking it during corrected execution would require a separate reentry, ordering, latency and GPU-completion contract. Neither material callback return nor the MID destruction fence is currently linked to a per-operation deferred-resource receipt.

The separate delayed proxy-release batch at `144351A30` is not a completion signal either. `1415E98A0` appends a proxy to that batch while the delayed flag `14435187E` is set, flushing on overflow through `1415ED070`. In threaded rendering, `1415ED070` copies the batch into a newly submitted render task and immediately clears the batch count; in the nonthreaded path it directly invokes each proxy's `+0x30` release virtual. `1415EF140` sets the delayed flag while publishing a render-fence task and an event at `1443518C0`. `1415EF6F0` dispatches the remaining batch, clears the flag, and waits that event. Therefore a zero batch count after dispatch does not establish that the release virtual has run, let alone that downstream RHI/GPU retirement is complete. The task/event ordering and its relation to the individual MID material operations still need a controlled receipt before they can be used for rollback.

Other native writers/consumers prevent a presentation-only shortcut. MID reset `141F14AC0` zeros the `+0xB8` vector count, can reallocate backing, queues proxy reset tasks, then reinitializes rows; it is outside the two vector/refresh task families already counted by the guard. `UMeshComponent_SetMaterial` at `141D86410` replaces an override slot, marks render state dirty, calls a material virtual, and, when a native physics body exists, invokes `142007950`. That callee updates body material/physics data and linked simulation fields. The C18 sample did not establish whether those 47 trace providers had native physics bodies, so no-feedback cannot be inferred from their MID parameter values or proxy occupancy alone.

For the sampled provider table `1438829C0`, constructor `141D8E9C0` installs virtual `+0x630` as `142100F30`, the getter used by `UMeshComponent_SetMaterial`. It returns a body pointer only when `141DC8D50` supplies a valid global and the selected body index (normally component `+0xBF0`) is within the component's array count at `+0xC38`; the pointer comes from the array at `+0xC30`. This identifies a narrow live witness for the selected providers: the indexed body-slot validity and `HasNativePhysicsBody` outcome at the actual setter. It does not establish either outcome for the retained C18 sample.

This supports a **partial** field layout only: `+0xB8` vector array header, `+0xF0/+0xF8/+0x100` proxy pointer slots, `+0x150..+0x1A8` twelve cache pointers, and `+0x1B0` destruction fence. At this original read-only checkpoint, proxy structure, full task ordering, render/GPU completion, and complete allocation bound remained unresolved. The later annotation pass below resolved a narrow proxy layout without proving task or GPU completion. The next production change needs an explicit strategy for logically dead/new owners and complete B, with a producer/writer exclusion or safe replay route; the entry census cannot supply that strategy.

The exact `UMaterialInstanceDynamic` class registration at `14260EAC0` supplies size `0x208` to `UE4_RegisterClassEx`, and the first proxy allocation requests `0x168` bytes. These establish individual object/proxy payload sizes for those paths, not a peak retained-memory bound: live addresses for proxy slots were published only as occupancy, allocator overhead and caches/backings/commands are additional, and corrected execution can retain simultaneous A, B, C and deferred owners.

It is applied only to the verified native-owner functions, leaving the earlier shared MID partial intact.
