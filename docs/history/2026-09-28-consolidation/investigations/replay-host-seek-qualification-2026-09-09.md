## Request and cancellation contract

`SeekOperation(Begin)` accepts a backward target between the supplied completed
application checkpoint and the current tick. `Read` reports the phase, failure,
origin, checkpoint, target, actual undo tick, pending work and commit decision.
`Held` means the exact requested tick is externally paused. `Release` detaches
the request; `Resume` remains a separate explicit action.

An interior origin may owe more simulation traversals before its application
can finish. The host finishes that work once before preparing B. Cancellation
during that completion remains pending: it does not discard native tails or
pretend to recreate a historical task. The resulting paused B is identified by
`undo_tick`, which can exceed `origin`. `original_recovered` is true only when
B recovery succeeds at the original request tick. A cancelled request must be
presented using its actual undo coordinate, not the earlier requested origin.

Capacity failure rejects new forward work while preserving the existing native
undo/release path. The local production-orchestration test verifies recovery
under a simulated accounting failure; no live over-budget allocation is claimed.

Before the commit decision, a failed wrapper delegates cancellation admission
to the existing restore transaction. That transaction checks complete B undo,
native membership/lifetimes, bindings and its execution domain. Rejection keeps
the owners intact. After commit becomes irreversible, cancellation is rejected.
Automatic native recovery is reflected as `Recovering`, then `Cancelled` only
after the native transaction reaches its recovered/releasable state.

## Release ownership

The last checkpoint pin cannot disappear at an unfinished world boundary.
Request release transfers it to the application owner without allocating.
The host retains CPU leases until the actual application tail completes and
retires native image references on their admitted render thread. A failed
retirement keeps ownership and blocks a new application; timeout is not GPU
cancellation.

The hold owns its surface `Draw`/`Release` event. Retirement cannot poll that
event while the hold is `Holding` or `Releasing`, even with an idle engine.
It is admitted only in `Idle`/`Resumed` with an idle application, engine and
world and no deferred engine-post callback. This prevents one owner from
consuming another owner's completion witness.

Outstanding checkpoint retirement can reject a new request. General queued or
coalesced requests, seeking repeatedly while held, and recoverable scene exit
are still separate unfinished lifecycle work.
